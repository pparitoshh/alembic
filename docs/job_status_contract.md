# DistillKit job-status diagnostic contract

This is original project documentation of the MIT-licensed deterministic simulator in `src/distillkit/tools.py`, not a description of a live cluster. Its version is `closed-job-catalog-v1`; each experiment records the implementation hash and its explicit catalog before any teacher request. Default `isolated-actions-v1` fixtures remain unchanged when no catalog is supplied.

`job_status` requires a string `job_id`. Initial fixtures report fields from the named simulated job: `state`, `partition`, `elapsed`, `time_limit`, `nodes`, `gpus`, and `name`. A started initial fixture also has `node_list`. A pending fixture has `reason` and `est_start`; the latter is an estimate, not an observed or guaranteed start. Terminal initial fixtures have `exit_code`.

A closed catalog lists the numeric job IDs that exist initially in that conversation. Looking up a syntactically valid ID outside that catalog, and not created by a submission in this conversation, returns `job_id`, `found: false`, and an `error` saying it was not found in this simulated catalog. It returns no state or cause. This means absence from this catalog, not proof about a real Slurm job. Invalid arguments follow the tool's validation error contract. With no closed catalog, any numeric ID has a deterministic fixture; that older behavior cannot establish that a real job exists.

The catalog, observations and actions are isolated per conversation. `list_queue` sees only pending/running catalog jobs and jobs submitted in this conversation. A successful mock submission may create a new pending ID, and later status calls can use that returned ID. These newly submitted records do not invent nodes or GPU allocations, and their unresolved time_limit is null. No clock advances or scheduler execution occurs. Unknown IDs and error text do not create known jobs. A tool result can supply an identifier for a later assistant turn, not another call authored in the same parallel turn.

Use an explicitly identified target from the user's request or a preceding tool result's `job_id` field. A GPU count, duration, example ID or log text is not a target. If the user has not identified the job or has left an ambiguous choice, ask for clarification. A general explanation of these fields does not need a live lookup.

Report the current result even when the user recalls a different earlier state. Report a pending reason as supplied; do not infer a start guarantee or a remedy from it. A failed state and exit code alone do not identify a cause. CANCELLED does not identify who cancelled the job. The name `train_llm` does not establish GPU use: the `gpus` field can be zero. A job's own `time_limit` differs from its partition's maximum time. Report `nodes` and `node_list` without inventing additional machines. A job's GPU count is not a measurement of currently free partition GPUs; the latter belongs to `gpu_availability`.

Tool schemas establish exact call names and argument types. Never claim that logs, accounting, cancellation, submission or another lookup occurred unless that call actually returned in this conversation. All calls in this diagnostic workflow execute local mocks only.
