# Resource-request parsing in job-status-policy-v3

The first scenario-plan pilot exposed seven blocked, explicitly requested read-only workflows. Six questions named resource checks in natural phrases such as “check the memory limits,” “check how many GPUs,” “check which partitions,” or “list all partition limits.” The v2 matcher required `free`, `available` or `partition` immediately after its few optional words and missed them. The other question said “my job with ID …,” which the job-target grammar missed.

For a new run, explicitly select `generate.job_status_policy_version: job-status-policy-v3` alongside the existing `generate.job_status_discovery` setting. The prompt version is `source-grounded-v8-self-contained-resource-policy`. The parser recognizes the documented resource capability inside a request clause, including a job's partition maximum and a GPU-per-node capacity requirement. Partition limits/capacities and free-GPU observations remain separate requested capabilities; a GPU allocation mentioned in a status question does not authorize a free-resource lookup. Explicit explanation-only clauses do not request live checks. This is still a bounded grammar and may reject other valid phrasing; it is not a complete natural-language authorization classifier.

Explicit prohibitions and ask-before-tool instructions still take precedence. V3 also recognizes “without using tools” and treats requests for examples or command instructions as explanation requests; “Can you check how many GPUs are free?” remains a live request. These tested phrases do not cover every possible explanation or prohibition. Missing or ambiguous job identifiers still require clarification. `job with ID` and `job with the number` are now recognized alongside existing explicit forms; an unrelated count or duration is not a target. Read-only restrictions, queue-discovery selection and result chronology are unchanged.

A resource filter must occur in the user request or in a preceding returned `partition` field. Omitted optional filters remain valid. Log text, error results, source/gold prompts and another call authored in the same batch cannot supply an unobserved filter. Both generation and replay apply the same policy, including exact application clarification/audit reconstruction.

Historical `job-status-policy-v2` remains the default for configurations that omit the new field and for callers constructing `JobStatusPolicy()` directly. Its original patterns, blocked attempts and support-review outcomes are preserved; they are not retrospectively executed or relabelled. Generation, direct bounded workflow calls, the diagnostic wrapper and verification resolve the configured version. A v2 row in a run explicitly configured for v3, or the reverse, fails the policy-consistency gate. Policy-free legacy paths retain their existing target grammar. The workflow record schema, source split, tool schemas and evaluation scorer protocols are unchanged.

Use a fresh run directory. Scenario-plan manifests bind the code and prompt bytes and reject a changed resume. Do not append to the first pilot's frozen outputs, overwrite its seven guard-origin transcripts, or present application-written clarification as a teacher answer. A support reviewer may legitimately find a future-intent preamble nonfactual; that does not make an incomplete guard-origin trace suitable for training.

`tests/test_resource_request_policy.py` exercises the actual `tool_trace`, request conversion, mock execution, `check_trace` and `verify.run` paths with a fake teacher. It covers the seven observed phrase shapes, preserved v2 replay, capability scope, negation, ambiguous/missing targets, user/preceding-result filter grounding, same-turn blocking and the remaining support gate. These tests do not establish real-model improvement and do not execute cluster actions. Frozen historical outputs and semantic review decisions stay separate from these code regressions.
