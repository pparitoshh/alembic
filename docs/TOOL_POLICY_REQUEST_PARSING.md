# Resource-request parsing in job-status-policy-v3

The first scenario-plan pilot exposed seven blocked, explicitly requested read-only workflows. Six questions named resource checks in natural phrases such as “check the memory limits,” “check how many GPUs,” “check which partitions,” or “list all partition limits.” The v2 matcher required `free`, `available` or `partition` immediately after its few optional words and missed them. The other question said “my job with ID …,” which the job-target grammar missed.

For a new run, explicitly select `generate.job_status_policy_version: job-status-policy-v3` alongside the existing `generate.job_status_discovery` setting. The prompt version is `source-grounded-v8-self-contained-resource-policy`. The parser recognizes the documented resource capability inside a request clause, including a job's partition maximum and a GPU-per-node capacity requirement. Partition limits/capacities and free-GPU observations remain separate requested capabilities; a GPU allocation mentioned in a status question does not authorize a free-resource lookup. Explicit explanation-only clauses do not request live checks. This is still a bounded grammar and may reject other valid phrasing; it is not a complete natural-language authorization classifier.

Explicit prohibitions and ask-before-tool instructions still take precedence. V3 also recognizes “without using tools” and treats requests for examples or command instructions as explanation requests; “Can you check how many GPUs are free?” remains a live request. These tested phrases do not cover every possible explanation or prohibition. Missing or ambiguous job identifiers still require clarification. `job with ID` and `job with the number` are now recognized alongside existing explicit forms; an unrelated count or duration is not a target. Read-only restrictions, queue-discovery selection and result chronology are unchanged.

A resource filter must occur in the user request or in a preceding returned `partition` field. Omitted optional filters remain valid. Log text, error results, source/gold prompts and another call authored in the same batch cannot supply an unobserved filter. Both generation and replay apply the same policy, including exact application clarification/audit reconstruction.

Historical `job-status-policy-v2` remains the default for configurations that omit the new field and for callers constructing `JobStatusPolicy()` directly. Its original patterns, blocked attempts and support-review outcomes are preserved; they are not retrospectively executed or relabelled. Generation, direct bounded workflow calls, the diagnostic wrapper and verification resolve the configured version. A v2 row in a run explicitly configured for v3, or the reverse, fails the policy-consistency gate. Policy-free legacy paths retain their existing target grammar. The workflow record schema, source split, tool schemas and evaluation scorer protocols are unchanged.

Use a fresh run directory. Scenario-plan manifests bind the code and prompt bytes and reject a changed resume. Do not append to the first pilot's frozen outputs, overwrite its seven guard-origin transcripts, or present application-written clarification as a teacher answer. A support reviewer may legitimately find a future-intent preamble nonfactual; that does not make an incomplete guard-origin trace suitable for training.

`tests/test_resource_request_policy.py` exercises the actual `tool_trace`, request conversion, mock execution, `check_trace` and `verify.run` paths with a fake teacher. It covers the seven observed phrase shapes, preserved v2 replay, capability scope, negation, ambiguous/missing targets, user/preceding-result filter grounding, same-turn blocking and the remaining support gate. These tests do not establish real-model improvement and do not execute cluster actions. Frozen historical outputs and semantic review decisions stay separate from these code regressions.

## Opt-in v4: partition node counts and explicit report requests

The second pilot exposed two further false positives: a user asked to compare a job's allocated nodes with its partition's total nodes, and another asked to check an explicitly named, possibly unknown partition and report its limits. V3 omits node counts from its partition-detail vocabulary and does not recognize the latter “tell me … report” request. The blocked calls were permitted by the visible read-only policy; their guard-authored, incomplete transcripts still must not be admitted as teacher answers.

For a fresh run, select `generate.job_status_policy_version: job-status-policy-v4` alongside an explicit `generate.job_status_discovery` setting such as `clarify_first`; the version field alone does not activate the bounded application policy. V4 recognizes partition node-count requests and bounded imperative/question forms of `report`, `provide` and `tell me/us`, alongside the previous resource verbs. A request must start its clause, optionally after `please`, a `can/could/would/will you` question or a `how can/could/do I` prefix. A historical attempt or a quoted manual instruction alone is not a request. Explanation/example/command questions, explicit prohibitions and excluded resource capabilities remain blocked. This remains a deliberately bounded grammar, not a complete natural-language permission classifier; unusual valid phrasing may still need clarification.

Independent review of the initial v4 candidate found five false permissions despite its passing CPU suite. The repaired matcher excludes fenced resource instructions, recognizes “what … means” as a definition request, and keeps only the positive resource scope before `excluding` or `without`. Thus a requested partition report can coexist with an excluded GPU query, and vice versa. “Without querying tools” prohibits every call under this policy. Closed fences permit a separate explicit request outside the example; an unclosed fence remains source text through the end of the question. This limited parsing does not establish general natural-language intent recognition. The added regressions preserve model attempts and check the real conversation guard plus replay; they do not establish teacher compliance.

The same exclusion applies to Markdown code lines beginning with four spaces or a tab, including a tab preceded by up to three spaces. A separate unindented request remains eligible. This deliberately fails closed: a legitimate resource request formatted with code-level indentation is also rejected and must be clarified or restated without that formatting. V2/v3 matching is unchanged.

The capability and target checks remain separate. Asking for partition node counts does not authorize free-GPU queries, queue discovery, job selection or state-changing actions. A supplied unknown partition name may reach the mock's error result without replacing the name. A filter inferred from job status requires that result in a completed earlier turn; source text, log lines, error results and simultaneous calls cannot establish it. The exact batch guard, read-only restriction, ambiguous-ID handling, source holdouts and support-review requirements remain active.

V2 remains the omitted-config/direct-caller default. V3 matching and its recorded blocks remain unchanged; no archived row is relabelled or retried. V4 is selected by the same explicit field in generation, bounded conversation calls, diagnostic orchestration and verification. An incompatible recorded/configured policy still fails verification, and a changed policy requires a fresh scenario-generation run. The prompt template, tool schemas, mock fixtures and evaluation scorer remain unchanged; the visible application-policy version identifies the new behavior.

`tests/test_resource_request_policy_v4.py` uses the real generation/conversation/replay/verification paths with a fake teacher and isolated deterministic mocks. It preserves the two v3 failures, checks their v4 execution, and tests prior positive shapes, no-authority/explanation/negation cases, wrong capabilities, malicious action attempts, target/result chronology and policy/config/resume consistency. The diagnostic orchestration test also includes v4 through the actual OpenAI client with fake HTTP. These CPU tests are integration checks, not real-model improvement evidence, and do not repair or promote existing pilot data.
